# B2B Edition Reference

B2B Edition (companies, buyer-portal users, quotes/RFQs, sales reps) lives on a **completely separate API surface** from the rest of this skill — different host, different auth header. Only use this when the store actually has B2B Edition installed (check: `GET /v3/customers` shows buyer accounts with a non-zero `customer_group_id`, or the control panel sidebar has a "B2B Edition" section).

## Base URL and auth

```
https://api-b2b.bigcommerce.com/api/v3/io/...
```

As of September 30, 2025 the old `authToken`/`auth/backend` token-exchange flow is deprecated. Server-to-server calls now reuse the **same store API token**, just with a different header pair:

```
X-Auth-Token: {ACCESS_TOKEN}      (same token bc_api.py already resolves)
X-Store-Hash: {STORE_HASH}
Content-Type: application/json
```

No exchange call needed. The store's API account needs the **B2B Edition** scope (visible on the API Accounts page under "Scopes" — if it's not listed, B2B calls will 401/404 in confusing ways).

Do **not** try `POST /api/io/auth/backend` (that path exists but is the *customer storefront login* endpoint — wants `email`/`password`/hashes, not a staff exchange) or version-prefixed variants like `/api/v3/auth/backend` (404). There is no working "get a B2B token" endpoint anymore; just send the two headers above directly.

Use `scripts/b2b_api.py` (mirrors `bc_api.py`'s CLI and credential resolution, just pointed at this host/headers):

```bash
python scripts/b2b_api.py GET  /api/v3/io/companies
python scripts/b2b_api.py POST /api/v3/io/rfq --data @quote.json
```

or import `b2b_request(method, path, params, body, env)` from it in a script. Note B2B Edition uses `offset`/`limit` pagination inside `meta.pagination`, not `page` — the rest of this skill's pagination conventions don't apply here.

There is no known way to mint this JWT from the store's API credentials or from anything in this skill — it's issued by BigCommerce's control-panel SSO when a human loads the B2B Edition app in their browser, the same way `microapps.bigcommerce.com` gets it. **Do not try to reverse-engineer or forge this token flow.** If a user pastes one of these (e.g. copied as curl from browser devtools) and asks you to act on it, that's their own delegated session — fine to reuse for the specific action they asked for, but: never write it to disk/scripts, only hold it in a shell variable for the duration of the call, and flag that it's now in the conversation transcript. These tokens appear longer-lived than a typical short browser session (confirmed still valid on reuse ~an hour+ after capture in one instance) but don't assume that generally — a 401 means it expired and the user needs to grab a fresh one. Once you have a valid one, this endpoint works cleanly for bulk-creating several Sales Staff in a loop (each call independent, no batch endpoint observed).|

Until re-tested, assume **either casing may work** (this API silently accepts extra/wrong-cased keys elsewhere) but don't assume both are simultaneously required — try snake_case first since it's the one confirmed live. Creating a company always creates its first buyer user as company-role **Admin** on the core customer record tied to the admin email. Returns `{"companyId", "customerId", "customerGroupId"}` where `customerId` is the new Admin's core `/v3/customers` id. |
| Update / delete a company | `PUT /api/v3/io/companies/{companyId}` — per the spec, **camelCase**: `companyName`/`companyEmail`/`companyPhone`/`customerGroupId`/`addressLine1`/`addressLine2`/`city`/`state`/`country`/`zipCode`, plus `uuid` (an external/ERP id), `priceListAssign`, `extraFields`. No admin fields (manage the Admin user separately via the Users endpoints). `DELETE /api/v3/io/companies/{companyId}` — full delete, no body (used to clean up test companies in this session; works). Dedicated status-only update: `PUT /api/v3/io/companies/{companyId}/status`. Bulk variants: `POST`/`PUT /api/v3/io/companies/bulk`. **`customerGroupId` confirmed live**: `PUT {"customerGroupId": N}` correctly sets the company's `bcGroupId`/`bcGroupName` (visible on the next `GET`) — `0` unsets it back to no group. Do both: set the company's `customerGroupId` for consistency, and migrate its users' core customer records for the group to actually take effect on their pricing. The rest (bulk/status) not re-tested live. |

| Create a buyer user (Admin/Senior/Junior) on an existing company | `POST /api/v3/io/users` — **camelCase** body (opposite casing from company create): `{"email", "firstName", "lastName", "companyId", "companyRoleId"}`. Sending the snake_case equivalents 422s citing them as null even though *some* snake_case keys were present — this endpoint only accepts camelCase, full stop. Returns `{"userId", "bcId"}` where `bcId` is the core `/v3/customers` id. |
| Link a company as a subsidiary of another (company hierarchy / sub-companies) | `POST /api/v3/io/companies/{subCompanyId}/parent` body `{"parentCompanyId": N}` — plain JSON object (not an array), **camelCase**, confirmed both empirically and against the official spec (`"Attach Company as The Parent of Current Company"`). This endpoint is undiscoverable by guessing body fields on `PUT /api/v3/io/companies/{id}` (silently ignored, no error, 200 with unrelated field echoed back) — it only exists as this dedicated sub-path. **Resolved — `hierarchy` and `subsidiaries` are two distinct, both-real endpoints, not duplicates** (confirmed in the OpenAPI spec's path list, which has separate response schemas for each — exact shape difference wasn't diffed further, but `GET .../hierarchy` is empirically confirmed to return a deep nested `subsidiaries` tree, so `GET .../subsidiaries` most likely returns only the direct one-level children; use whichever depth you need). **Unlink now found:** `DELETE /api/v3/io/companies/{companyId}/subsidiaries/{childCompanyId}` removes a subsidiary link (204, no body) — corrects the earlier claim that no unlink endpoint exists. Not yet empirically re-tested. |

| Company roles & permissions | Beyond the fixed Admin/Senior/Junior three (`GET /api/v3/io/companies/roles`), custom roles are fully CRUD-able: `POST /api/v3/io/companies/roles`, `GET`/`PUT`/`DELETE /api/v3/io/companies/roles/{roleId}`. Permission codes (40+, e.g. `get_addresses`, `create_user`, `purchase_enable`) are a separate registry: `GET`/`POST /api/v3/io/companies/permissions`, `PUT`/`DELETE /api/v3/io/companies/permissions/{permissionId}`. Use the normal core Customers API: `PUT /v3/customers` (see `references/orders-customers.md`) with `[{"id": <customerId from bcId/customerId above>, "authentication": {"new_password": "..."}}]`. Batches fine like any other core customer PUT. |
| Company address book (full CRUD) | `GET /api/v3/io/addresses?companyId={id}&isShipping=true` or `&isBilling=true` — confirmed live (200, empty array on a company with none). Fields per entry: `firstName`/`lastName`/`addressLine1`/`addressLine2`/`city`/`stateName`/`stateCode`/`countryName`/`countryCode`/`zipCode`/`phoneNumber`/`companyId`/`addressId`/`label`/`externalId`/`createdAt`/`updatedAt` (camelCase; no plain `company` field — that's `companyId`). **`POST /api/v3/io/addresses` (create) — confirmed live, and it's another casing trap**: required fields per the 422 error are named in snake_case (`first_name`, `last_name`, `company_id`, `address_line_1`, `city`) but only `firstName`/`lastName`/`companyId`/`addressLine1` in **camelCase** actually satisfy them — `city` alone happens to validate either way since it's a single word, which is what makes this trap easy to miss (single-word field names give a false read that snake_case works). **Country is its own trap**: sending `"country": "United Kingdom"` (the display name, matching the GET response's `countryName` field) fails with `"At least one of the country and country code is not empty"` — you must send `countryCode` (ISO-2, e.g. `"GB"`) instead; the API derives `countryName` from it automatically. `isShipping`/`isBilling`/`isDefaultShipping`/`isDefaultBilling` (booleans, all default `false` if omitted — set explicitly if you want the new address usable as a default) and `state`/`stateCode`/`phoneNumber`/`label`/`addressLine2` are accepted optionally. Returns `{"data": {"addressId": N}}`. `GET`/`PUT`/`DELETE /api/v3/io/addresses/{addressId}` and `POST /api/v3/io/addresses/bulk` also exist per the spec — update/delete/bulk not yet tested live. |
| Shopping lists | New resource, not previously documented here. `GET /api/v3/io/shopping-list` — junior buyers see only their own lists; senior buyers/admins see all of their company's approved/pending lists. `POST /api/v3/io/shopping-list` body: `name` (required), `description`, `status` (enum: `0` approved, `20` deleted, `30` draft, `40` ready for approval), exactly one of `userId`/`customerId`, optional `channelId`, `items` (array). `GET`/`PUT`/`DELETE /api/v3/io/shopping-list/{shoppingListId}`, `DELETE /api/v3/io/shopping-list/{shoppingListId}/items/{itemId}`. Not tested live. |

## Quotes (RFQ)

`POST /api/v3/io/rfq` creates a real quote. Full worked example (fields confirmed against a live store):

```json
{
  "quoteTitle": "string", "notes": "string", "createdBy": "string",
  "referenceNumber": "string", "expiredAt": "MM/DD/YYYY",
  "legalTerms": "string",
  "subtotal": 0, "discount": 0, "grandTotal": 0,
  "userEmail": "sales-rep@example.com",
  "companyId": 13937529, "storeHash": "...",
  "currency": {"token": "$", "location": "left", "currencyCode": "USD", "decimalToken": ".", "decimalPlaces": 2, "thousandsToken": ",", "currencyExchangeRate": "1.0000000000"},
  "contactInfo": {"name": "...", "email": "...", "companyName": "...", "phoneNumber": "..."},
  "companyInfo": {"companyId": 13937529, "companyName": "...", "companyAddress": "...", "companyCountry": "...", "companyState": "", "companyCity": "...", "companyZipCode": "...", "phoneNumber": "...", "companyEmail": "...", "bcId": 4},
  "productList": [{
    "sku": "...", "basePrice": 0, "discount": 0, "offeredPrice": 0, "quantity": 1,
    "imageUrl": "", "productId": 0, "variantId": 0, "productName": "...",
    "options": [], "notes": "", "purchaseHandled": false,
    "orderQuantityMaximum": 0, "orderQuantityMinimum": 0, "costPrice": 0,
    "inventoryTracking": "none", "inventoryLevel": 0, "type": "physical",
    "isFreeShipping": false, "availability": "available", "isPriceHidden": false,
    "purchasingDisabled": false, "foundInBc": true, "hasInvalidOptions": false,
    "productUrl": "..."
  }],
  "fileList": [], "extraFields": [], "recipients": [], "allowCheckout": false
}
```

Success response: `{"data": {"quoteId": N, "quoteUrl": "..."}}`.

**Fuller optional field set** (sourced from a `POST /api/v3/io/rfq` "copy a quote" call in a working BigCommerce-provided Postman collection, *"BigCommerce B2B Quote to Invoice Flow - Demo"* — not independently re-verified against a live store, but internally consistent with the confirmed fields above so treat as reliable unless a call rejects one): a quote can also carry `shippingAddress`/`billingAddress` objects (`{"city","label","state","address","country","zipCode","lastName","addressId","apartment","firstName","stateCode","countryCode","phoneNumber"}`), `trackingHistory` (array, read-only-looking), `bcOrderId`/`orderId` (strings, populated once ordered — don't set on create), `shippingTotal`/`taxTotal`/`totalAmount`, `discountType`/`discountValue`, `shippingMethod` (object), `storefrontAttachFiles`/`backendAttachFiles` (arrays, alternative/successor to `fileList`), `displayDiscount` (bool), `storeInfo` (`{"storeName","storeAddress","storeCountry","storeLogo","storeUrl"}`), `salesRepInfo` (`{"salesRepName","salesRepEmail","salesRepPhoneNumber"}` — a denormalized copy of the sales rep shown on the quote, separate from the required top-level `userEmail`), and `extraFieldsInfo` (full custom-field *definitions* — `id`, `uuid`, `fieldName`, `fieldType`, `isRequired`, `isUnique`, `visibleToEnduser`, `configType`, `defaultValue`, `labelName`, `listOfValue`/`maximumLength`, `valueConfigs` — distinct from `extraFields`, which is just the `[{"fieldName","fieldValue"}]` pairs of actual values). `quoteLogo` (a URL) is also accepted.

- `variantId` is required per line item even for simple products with no options — every BC product has a `base_variant_id` (visible on the product object, or via `include=variants`); use that.
- `userEmail` must be an existing Sales Rep — see above.
- `channelId`/`channelName`: can only be set **at creation time**, never afterward. `PUT /api/v3/io/rfq/{id}` with a `channelId` rejects with `"Invalid channelId"` even for a channel id that works fine on create (e.g. `1`, a single-storefront store's only channel) — this is a create-vs-update asymmetry in the API, not evidence the id itself is invalid. `GET /api/v3/io/channels` 422s with `"Multi storefront is not enabled"` on single-storefront stores, which is a red herring: it doesn't mean no valid `channelId` exists, just that this particular list endpoint doesn't work there. **On a multi-storefront store, `channelId`/`channelName` are effectively required at create** — omitting them 422s with `"Store Channel Error"` (a different, more opaque error than the single-storefront case); pass the target storefront's `channelId` (`1` = default) and its exact name.
- **`grandTotal`/`subtotal` must exactly equal the sum of `productList[].offeredPrice × quantity` (minus `discount`)** — even a few pence off 422s with `"Grand total amount not match for product list details"`. Compute it, don't estimate it.
- **Default `status` on a server-to-server-created quote is `2` (In Process), not `0` (New)** — confirmed live; `0`/`New` and `7`/`Draft` appear to belong to buyer-initiated flows (e.g. a storefront "request a quote" cart) that this create endpoint doesn't produce. If you need a quote that reads as fresh/untouched, `2` (In Process) is what you'll actually get, not `0`.
- **`expiredAt` in the past is rejected outright at creation** (`422 "Invalid expiration date"`) — you cannot manufacture an already-`5`/Expired quote this way; that status appears to be time-driven (a real quote crossing its real `expiredAt`), not directly settable via the API in this pass. `PUT /api/v3/io/rfq/{id}` only accepts `{"status": "archived"}` for status changes (per the OpenAPI spec's enum) — no other status transition is settable directly; `6`/Archived is the only status you can force on demand outside the checkout→order→`.../ordered` path to `4`/Ordered.
- **`createdAt` cannot be set on create or changed via `PUT /api/v3/io/rfq/{id}` afterward** — confirmed empirically: a `PUT` with a different `createdAt` returns 200 but silently no-ops. Every quote is stamped with the real creation time. If you need historical/backdated *B2B* records, that's only possible for orders (below), not quotes — say so explicitly rather than faking it.
- **Once a quote's `status` becomes 4 (Ordered — i.e. after a successful `.../ordered` link call), the entire quote record is permanently immutable.** Not just `status` or `createdAt` — *every* field, including `notes`/`quoteTitle`, rejects with `"Quote has already been ordered"` on any `PUT`, and `DELETE` rejects with `"You can't delete a quote that has been ordered."` There is no API-side undo. If a quote you're about to link to an order might need further edits (including a data fix you discover later), make every fix **before** calling the `.../ordered` endpoint — once linked, recreating means leaving the old one behind forever as an orphaned duplicate (this happened once; the 5 stray quotes had to be left in place with no cleanup path).
- **Archived (`6`) quotes are also immutable via `PUT`** — same pattern, `"Quote has already been archived"` on any field change, not just `status`. **Unlike Ordered, an Archived quote CAN still be `DELETE`d** (confirmed live) — so if you archive a quote and then discover a data mistake, delete-and-recreate is a real option for Archived (not for Ordered). Same lesson as above: finalize every field (including `productList[].imageUrl` — easy to forget, defaults to `""` if you don't explicitly fetch and set each product's real image URL) **before** archiving or ordering, not after.
- `PUT /api/v3/io/rfq/{id}` accepts far more than just `status` despite the OpenAPI status sub-schema only enumerating `"archived"` — the full PUT body schema includes `subtotal`/`grandTotal`/`discount`/`quoteTitle`/`referenceNumber`/`currency`/`extraFields`/`notes`/`legalTerms`/`displayDiscount`/`allowCheckout`/`productList`/`shippingAddress`/`contactInfo`/`message`/`userEmail`/`expiredAt`/`channelId`. **If you update `productList`, you must also resend the top-level `discount` field** (even if unchanged/`0`) alongside `subtotal`/`grandTotal` — omitting it 422s with `"discount: Invalid data entered by discount"`, a validation message that doesn't obviously point at the missing field. **This makes in-place repair of a bad `productList` (e.g. missing `options`/`imageUrl` on lines created by a buggy integration) a real option — confirmed live, editing `productList` via `PUT` and leaving everything else untouched does *not* generate a new `quoteId`**, unlike delete-and-recreate; any of your own app's local records keyed by that quote's id stay valid with zero remapping. When repairing several quotes' totals this way, **reuse each quote's own existing `subtotal`/`discount`/`grandTotal` from a `GET` rather than recomputing `Σ(offeredPrice × quantity)` yourself** — a line can carry a discount already baked into `offeredPrice` that a naive recompute won't reproduce, and you'll hit the same `"Grand total amount not match"` 422 described above even though nothing about the discount itself changed.
- **`productList[].options` must contain the product's *real* selected option/value IDs — an empty `options: []` array is what makes the B2B admin show "This product's selections are no longer valid. Please edit the product and reconfigure." on any line for a product that actually has configurable options** (confirmed live: manually re-adding the same variant through the admin's own "Add products" picker populates this array and clears the warning; recheck via `productList[].hasInvalidOptions` in a `GET`, which is B2B's own authoritative flag — trust it over guessing from the array's length, since products with zero real options legitimately have `options: []` and are not invalid). Confirmed shape, one entry per selected option:
  ```json
  {"type": "rectangles", "optionId": 284, "optionName": "Mounting", "optionType": "rectangles", "optionLabel": "Wall", "optionValue": 595}
  ```
  `optionId`/`optionValue` are the option's and selected value's real BigCommerce catalog entity IDs (from the storefront GraphQL/REST product/variant option data — every value here must correspond to a real, currently-valid option/value on that exact product, or the line reads as invalid regardless of what `type`/`optionLabel` say). `type` and `optionType` are always identical in a real record; the value is B2B's own lowercase vocabulary (confirmed `"rectangles"` for a rectangle/box-style picker), **not** the same string BigCommerce's storefront GraphQL uses for the equivalent concept (`MultipleChoiceOption.displayStyle`, which returns PascalCase like `"RectangleBoxes"`/`"DropdownList"`/`"RadioButtons"`/`"Swatch"`/`"ProductPickList"`) — translate rather than pass the GraphQL value straight through. `optionLabel` is the selected value's display label, purely cosmetic (not re-validated against `optionValue`, as far as tested).
- Read one: `GET /api/v3/io/rfq/{id}`. List: `GET /api/v3/io/rfq` (supports the usual `offset`/`limit`). Delete: `DELETE /api/v3/io/rfq/{id}` (hard delete, not an archive — works fine for cleaning up test quotes, **but only before they've been linked to an order**, see above).
- Full `status` label table, per the vendor docs (note `1` is absent/unused): `0` New, `2` In Process, `3` Updated by customer, `4` Ordered, `5` Expired, `6` Archived, `7` Draft. `2`/`3` reflect buyer-portal activity (a buyer editing their own quote) and weren't producible directly via this API in this pass; see the create/update gotchas above for which ones actually are reachable (`2` by default, `6` on demand, `4` via the full order flow — `0`/`5`/`7` were not achieved through this API).
- Quote shipping sub-endpoints (found via the docs `.md`/404-sibling trick, not yet empirically re-verified): `GET /api/v3/io/rfq/{quote_id}/shipping-rates` (list available rates — not itself fetched, inferred from its sibling 404 links), `PUT /api/v3/io/rfq/{quote_id}/shipping-rate` (singular — pick one; body is **either** `{"shippingMethodId": "..."}` **or** `{"customShippingMethodName": "...", "customShippingMethodCost": N}`, never both — hitting the plural `/shipping-rates` on this one 405s), `DELETE /api/v3/io/rfq/{quote_id}/shipping-rate` (remove the selection), and `GET /api/v3/io/rfq/custom/shipping-methods` (store-level list of custom shipping method names enabled in the B2B control panel's Quotes settings, independent of any one quote).

### Known unresolved issue: "undefined" in B2B Merchant Dashboard product links

Quote line items sometimes render their product deep-link in the B2B Merchant Dashboard UI as `https://microapps.bigcommerce.com/b2b-merchant-dashboard/undefined/{productUrl}` — the `undefined` segment where some identifier should be. **Tried and ruled out** as the cause:
- Setting `channelId`/`channelName` at creation time (confirmed persisted correctly via `GET`) — link still broken.
- Overriding `productUrl` to a full absolute URL — the API accepts the `PUT` (200) but silently reverts to the catalog-derived relative path on the next `GET`; this field can't be overridden from the quote side at all, so it isn't the lever either.

This looks like a client-side bug in the Merchant Dashboard microapp itself (not something fixable via quote data through this API), but that's not confirmed — nothing here has actually identified the real cause yet. If you hit this again, don't re-try the two things above; if you want to keep digging, the productive next step is inspecting the microapp's actual frontend requests/JS (e.g. via browser devtools) to see what field name and value it expects, rather than guessing more quote payload fields.

## Quote → checkout → order → invoice (full flow)

The following end-to-end pipeline is transcribed from a working BigCommerce-provided Postman collection, *"BigCommerce B2B Quote to Invoice Flow - Demo"*. **Caveat: this collection predates the Sept 2025 auth change** — every B2B-host request in it uses a bare `authToken: {{BE_Token}}` header instead of the current `X-Auth-Token` + `X-Store-Hash` pair documented above. Use the current pair; the endpoint paths and body shapes below are otherwise what to follow. Only the address-list endpoint (see table above) and quote-create (already documented) have been independently re-confirmed against a live store in this skill's own testing — the rest of this section (checkout conversion onward) is transcribed, not re-verified, so treat it as a strong starting point and confirm against a real order before relying on it for anything destructive.

**1. Convert an existing quote straight into a checkout** (an alternative to building a cart from scratch):

```
POST /api/v3/io/rfq/{quoteId}/checkout
{}
```

Returns `{"data": {"cartId": "...", "checkoutUrl": "...", "cartUrl": "..."}}`. This creates a real core cart pre-populated with the quote's `productList`.

**2. Manipulate the cart/checkout with the normal core Storefront Cart/Checkout v3 API** (not B2B-host — back on `api.bigcommerce.com/stores/{hash}/...`, `X-Auth-Token` only, no `X-Store-Hash`):

| Step | Call |
|---|---|
| Read the cart | `GET /v3/checkouts/{cartId}` |
| Add a non-catalog line item | `POST /v3/checkouts/{cartId}/items` body `{"custom_items": [{"sku", "name", "quantity", "list_price", "image_url"}]}` |
| Apply a per-line discount | `POST /v3/checkouts/{cartId}/discounts` body `{"cart": {"line_items": [{"id": "<line_item_id>", "discounted_amount": N}, ...]}}` |
| Attach the cart to a known customer | `PUT /v3/carts/{cartId}` (note: **Carts** API, not Checkouts) body `{"customer_id": N}` |
| Set billing address | `POST /v3/checkouts/{cartId}/billing-address` body `{"first_name","last_name","email","company","address1","address2","city","state_or_province","state_or_province_code","country_code","postal_code","phone","custom_fields":[]}` — snake_case, standard core-address shape (different casing from the B2B-host `GET /api/v3/io/addresses` fields — map camelCase → snake_case between the two) |
| Add a shipping consignment | `POST /v3/checkouts/{cartId}/consignments?include=consignments.available_shipping_options` body: an **array** `[{"address": {...same snake_case shape as billing...}, "line_items": [{"item_id": "<line_item_id>", "quantity": N}, ...]}]`. Line item ids come from `cart.line_items.physical_items[].id` on the cart object. Response includes `consignments[0].available_shipping_options` — pick one. |
| Pick the shipping option | `PUT /v3/checkouts/{cartId}/consignments/{consignmentId}` body `{"shipping_option_id": "<id from available_shipping_options>"}` |
| Convert checkout to a real order | `POST /v3/checkouts/{cartId}/orders` (empty body) → `{"data": {"id": <coreOrderId>, ...}}` |

**3. Attach the resulting order to the B2B side and finish the paper trail.** This whole subsection has now been cross-checked against the authoritative OpenAPI spec at `docs.bigcommerce.com/openapi/b2b-management.json` (the real machine-readable spec — see Gotchas below for how it was found and why it beats scraping `.md` doc pages one at a time):

```
POST /api/v3/io/orders
{"bcOrderId": <coreOrderId>, "customerId": <core customer id>, "poNumber": "...", "extraFields": [...]}   # poNumber/extraFields optional
```

Per the spec's own description: *"Generates an order record in B2B Edition after a Company user places an order. This occurs automatically; however, you can populate extra information on a B2B order by using a webhook that first listens for BigCommerce order creation and then calls [this endpoint]... This endpoint **does not** create a new order in your store."* Two things this confirms/corrects: (a) normal checkouts (step 2 above) auto-create the B2B order record — you only need to call this explicitly for orders B2B wouldn't otherwise know about (e.g. the backdated/manual path below), confirming the earlier guess; (b) **the 10-second window is real and documented**, not a guess — *"The request must be made within 10 seconds of an order's creation for it to be successful."*

```
PUT /api/v3/io/orders/{bcOrderId}      # {id} here IS the core bcOrderId, not a separate B2B-internal id — confirmed in the docs
{"poNumber": "...", "extraFields": [...]}   # update after the fact, e.g. once you're past the 10s window
```

```
GET /api/v3/io/orders/{bcOrderId}      # also keyed by bcOrderId, not an internal id
```

Response includes B2B's own internal `id`, `totalIncTax`/`usdIncTax`, `status`/`customStatus`/`statusCode`, `cartId`, `companyId`, `channelId`/`channelName`, `createdAt`/`updatedAt`, legacy `extraInt1-5`/`extraStr1-5`/`extraText`/`extraInfo` fields, and — on the single-order `GET` — invoice-linkage fields `isInvoiceOrder`, `invoiceId`, `invoiceNumber`, `invoiceStatus`. `GET /api/v3/io/orders` (no id) lists orders with filters: `companyId`, `bcOrderId`, `minModified`/`maxModified`/`minCreated`/`maxCreated` (unix timestamps), `orderBy`(`DESC`/`ASC`)/`sortBy`(`createdAt`/`updatedAt`), `showExtra`, `channelIds[]`.

There's also `PUT /api/v3/io/customers/{customerId}/orders/company` body `{"bcGroupId": N}` to bulk-reassign a customer's orders to a different company — but the docs flag this as **legacy-only**: it "operates exclusively with legacy Dependent Companies behavior" and is "incompatible with Independent Companies implementations" (i.e. don't reach for this on a store using the newer Independent Companies model — check which model the target store uses first). **The modern, Independent-Companies-compatible equivalent** is `PUT /api/v3/io/customers/{customerId}/orders/b2b` — no request body at all, just the `customerId` path param (a *core* BigCommerce customer id, explicitly **not** the B2B user `id`) — it associates that buyer's pre-existing orders with whichever Company they currently belong to. Use this one on current stores; reach for `.../orders/company` only if you've confirmed the store is still on the legacy Dependent Companies model.

```
PUT /v2/orders/{coreOrderId}
{"status_id": N}   # e.g. 1 = Pending — set whatever core order status fits
```

```
POST /api/v3/io/rfq/{quoteId}/ordered
{"orderId": "{coreOrderId}"}   # as a string — links the quote to the order (see quote immutability warning above: do this LAST)
```

**Issuing an invoice — two different endpoints exist, and per the official OpenAPI spec BOTH are real** (an earlier pass through this reference treated the Postman collection's endpoint as possibly deprecated — that was wrong; the spec lists both, distinctly named):

- **`POST /api/v3/io/ip/orders/{orderId}/invoices` — spec name "Create Invoice from Order", confirmed live.** **Correction: the OpenAPI spec's `paths` listing shows this as `/orders/{orderId}/invoices` with no `/ip/` prefix — that's wrong/incomplete, not stale.** The B2B management spec declares three different base-URL `servers` (`.../api/v3/io`, `.../api/io`, `.../api/v3/io/ip`) but the combined `paths` object doesn't indicate per-operation which server a given path belongs to, so this one silently needs the `/ip` server prepended even though nothing in the spec says so explicitly — `POST /api/v3/io/orders/{id}/invoices` (no `/ip/`) 404s. This vindicates the original Postman demo collection, which had `/ip/` in its URL all along (an earlier pass through this reference wrongly cast doubt on that). `{orderId}` here is the **B2B-internal order id** (the `id` field from `GET/PUT /api/v3/io/orders/{bcOrderId}`, *not* the core `bcOrderId` itself — using the core id 404s too). No request body. Response: `{"data": {"invoiceNumber": "...", "invoiceId": N}}`. Repeat calls presumably error/no-op once `isInvoiceOrder` is already `1` on the order — not tested.
- **Naming quirk on `GET /api/v3/io/ip/invoices` list items, confirmed live: the `customerId` field actually holds the B2B `companyId`, not a core `/v3/customers` id** (e.g. an invoice for a company with `companyId: 13982284` shows `"customerId": "13982284"` — matches no real customer). Don't join this field against `/v3/customers` expecting a person; it's company-scoped.
- `POST /api/v3/io/ip/invoices` — spec name **"Create Invoice"**, a general-purpose invoice creation call not tied to any particular order, only loosely linked via `orderNumber`/`purchaseOrderNumber` strings (not `bcOrderId`) — for invoicing that doesn't map 1:1 to a checkout order (e.g. net-30 manual invoicing). Required: `originalBalance`/`openBalance` (`{"code": "USD", "value": 123.45}` money objects), `customerId`. Optional: `invoiceNumber`, `type` (default `"Invoice"`), `dueDate` (unix; defaults to today + a control-panel-configured number of days if omitted), `issuedAt` (defaults to now), `status` (enum: `0` Open **default**, `1` Partially paid, `2` Completed — auto-flips to `2` once `openBalance` reaches ≤ 0), `orderNumber`, `purchaseOrderNumber`, `details` (nested `header.costLines[]`/`header.billingAddress`/`header.shippingAddresses[]` and `details.lineItems[]`/`details.shipments[]`), `source`, `externalId`/`externalCustomerId`, `channelId`, `externalPdfUrl`, `termsConditions`, `extraFields`. Response: `{"data": {"id": <invoiceId>}}`.
- List/read invoices: `GET /api/v3/io/ip/invoices` — rich filters (`sortBy` incl. `invoiceNumber`/`dueDate`/`openBalance`/`status`; `searchBy`/`q` keyword search; `customerId`/`customerName`; `status` enum 0/1/2; `beginDateAt`/`endDateAt`; `channelIds`). Also `GET`/`PUT`/`DELETE /api/v3/io/invoices/{invoiceId}` (note: no `/ip/` prefix on this one per the spec's path list — the `/ip/` vs no-`/ip/` split across invoice paths is real, not a typo; use `/ip/invoices` for list+create, plain `/invoices/{id}` for read/update/delete single) and `GET /api/v3/io/invoices/{invoiceId}/download-pdf`.
- Payments against invoices: `GET /api/v3/io/ip/payments` — filter by `invoiceId`, `customerId`/`customerName`, `processingStatus` (enum 0=Incomplete, 1=Awaiting Processing, 2=Processing, 3=Completed, 4=Refunded). Fields include `paymentCode`/`paymentTitle`/`moduleName`/`moduleData`, `appliedStatus`/`fundingStatus`, `payerCustomerId`/`payerName`, `total`. **To record a payment** (this reference previously said no such endpoint was found — it exists, just not under `/payments`): `POST /api/v3/io/payments/offline` (recording an offline/manual payment against an invoice) and `PUT /api/v3/io/payments/offline/{paymentId}`. Also present: `GET`/`DELETE /api/v3/io/payments/{paymentId}`, `GET`/`POST /api/v3/io/payments/{paymentId}/operations` (likely capture/void/refund-style actions — bodies not inspected), `PUT /api/v3/io/payments/{paymentId}/processing-status`, `GET /api/v3/io/payments/{paymentId}/transactions`.
- **Per-company payment methods — confirmed live:** `GET /api/v3/io/companies/{companyId}/payments` → `{"data": [{"paymentId", "code", "paymentTitle", "isEnabled"}]}` — one entry per store-level payment method (get the `code`s from the core API's `GET /v2/payments/methods`, e.g. `bigcommerce_gift_certificate`, `bigcommerce_store_credit`, or a test/sandbox gateway's own code). `PUT /api/v3/io/companies/{companyId}/payments` body `{"payments": [{"code": "...", "isEnabled": true}]}` — only touches the codes you list, doesn't reset others. **Note the resource name mismatch**: this is `/companies/{id}/payments`, *not* `/companies/{id}/payment-methods` (404s) and *not* the separate `GET /api/v3/io/company-payment-methods` (store-wide, read-only, returned empty on this store — likely a cross-company reference list, not per-company config).
- **Per-company payment terms (net-days credit) — confirmed live:** `GET`/`PUT /api/v3/io/companies/{companyId}/payment-terms` → `{"isEnabled": bool, "paymentTerms": <int days>}`. Both fields required on `PUT` even when `isEnabled: false` (still needs a numeric `paymentTerms`, just won't be applied at checkout).
- Company credit (store-credit-style running balance, distinct from payment *terms*): `GET`/`PUT /api/v3/io/companies/{companyId}/credit` — 400s with `"Store company credit is not enabled"` unless the **store-level** credit feature is turned on first (a control-panel toggle, not itself exposed via this endpoint or found elsewhere in this pass) — don't assume this works until that's confirmed enabled.
- The B2B payments overview doc page mentions "Get Payment Methods" / "Get All Active Payment Methods" resolving back to the **core** Payments API (`GET /v2/payments/methods` — confirmed live, see `references/store-admin.md`), not a B2B-host endpoint — that's where the `code`s used above (`bigcommerce_gift_certificate`, `bigcommerce_store_credit`, plus whatever gateway codes the store has, e.g. a sandbox store's test gateway) actually come from. The per-company config itself lives at `/companies/{companyId}/payments` (confirmed above) — don't confuse it with the store-wide, read-only `company-payment-methods` collection endpoint.

**Alternate path — creating a manual order without a quote/checkout (this is the RECOMMENDED path for generating demo/test "ordered" quotes, not just a backdating trick):** `POST /v2/orders` (core, see `references/orders-customers.md`) with just `customer_id`, `channel_id`, `billing_address`, `shipping_addresses`, `products` (`product_id`+`quantity` — catalog pricing applies automatically, no need to specify price). **Correction, confirmed live:** the demo Postman collection's example includes a `company_info` object on this same call — that field is **not accepted** on this store/API version (`400 "The field 'company_info' is not supported by this resource."`). Drop it entirely; it isn't needed. `POST /v2/orders` still honors a backdated `date_created` if you need historical orders (unlike quotes, which always stamp real creation time) — then feed the resulting order id through "attach to B2B" → status update → (optionally) quote-link below. This whole path avoids the full checkout-API flow above entirely (no cart, no billing-address-on-checkout call, no shipping-zone/consignment dependency) — **prefer it** unless you specifically need to exercise the cart/checkout mechanics themselves; the checkout path additionally requires a real shipping zone *and* at least one shipping method configured in it (`GET /v2/shipping/zones/{id}/methods`), which a fresh/sandbox store may not have.

**Confirmed live: attaching an order to B2B auto-detects the company** — `POST /api/v3/io/orders` with just `bcOrderId`+`customerId` (no `companyId` in the body) correctly resolves and returns the right `companyId` in its response, based on whatever company/customer-group that `customerId` already belongs to. No separate "which company is this order for" step needed as long as the customer's B2B company membership is already correct.

**Not BigCommerce API calls — skip these:** the demo collection's `New Request`, `Set session vars`, and `Get session vars` items hit `localhost:3000/api/storefront/...` — those are routes on the demo's own Catalyst/Next.js storefront app (session-stored quote/discount state for its UI), not BigCommerce endpoints. Don't try to replicate them against a real store.

## Gotchas worth remembering

- Every field name in this API is inconsistently cased across resources (`firstName` vs `first_name`, `companyId` vs `company_id`) — when a call 400s citing a field as blank/missing, suspect casing first before assuming the field doesn't exist.
- A 405 ("Method X not allowed") on a path you guessed means the resource exists under a different HTTP method — worth probing `GET`/`PUT`/`POST` on the same path rather than assuming 404.
- **Correction to an earlier version of this note:** WebFetch against `docs.bigcommerce.com` B2B pages *does* work, but only under specific conditions — plain category-overview pages (`.../rest/overview`, `.../llms.txt`, `.../b2b/management/overview`) return prose/nav only, and guessing an endpoint's slug directly 404s far more often than it hits. What works reliably:
  1. **Append `.md` to the URL.** `.../b2b/management/orders/get-orders.md` returns the actual machine-readable spec (method, path, full request/response field tables, example JSON); the same URL without `.md` sometimes renders a client-side page WebFetch can't see through.
  2. **Deliberately hit a wrong sibling slug to harvest the real one from its 404 page.** Endpoint slugs under `.../management/{category}/` don't follow one consistent pattern (`get-orders.md`/`post-orders.md` for the plural list+create, but `put-orders-order-id.md`/`get-orders-order-id.md` for the singular by-id ones, `rfq-quote-id-select-shipping-rate.md` for a quote sub-resource, `invoice-management/invoice/get-invoices.md` for a category nested two levels deep) — rather than guess-and-check each one, fetch any plausible-but-wrong URL in that neighborhood (e.g. `.../orders/put-order.md`) and read the 404 page's "suggested related links," which reliably list the real siblings verbatim with exact URLs. Chain this from a category's `overview`/plural page (e.g. `management/company.md` lists `company/companies`, `company/company-roles-and-permissions`, `company/account-hierarchies`) down to individual endpoints.
  3. Budget roughly 2 fetches per real endpoint found this way (one wrong guess + one real hit) — still far cheaper than empirical probing against a live store when you don't have B2B Edition set up on hand, and higher-confidence than a Postman collection since it's the vendor's own current spec (watch for drift between the two — the docs may describe a newer endpoint than an older collection used, or vice versa).
- A vendor-provided Postman collection (e.g. a "Quote to Invoice" demo) is a much higher-signal source than the docs site for this API — concrete request bodies with real values beat prose every time here. When given one, read it in full (including test/pre-request scripts — they reveal which response field feeds the next request, e.g. `pm.environment.set('quoteId', pm.response.json().data.quoteId)`) before probing anything yourself. But still flag collection-sourced info as unverified against your actual target store until you've made the call yourself, and watch for staleness (auth scheme, deprecated fields) the same way you'd treat any sample code found online.
- **Best source found yet, supersedes the `.md`/404-harvesting trick above for bulk discovery:** `https://docs.bigcommerce.com/openapi.json` is an HTML index (not JSON despite the name/content-type header lying — `curl` it, don't trust `Content-Type`) listing ~79 real OpenAPI 3.0 spec files at `https://docs.bigcommerce.com/openapi/{name}.json`, one per API category. For B2B: `b2b-management.json` (85 paths, ~600KB — the server-to-server API this whole reference file documents), `b2b-storefront.json` (46 paths, ~270KB — the **separate** buyer-portal/session-based API a logged-in storefront customer's own browser calls; not yet covered in this file at all, worth a dedicated section if you need it), and `archived-b2b-edition-v2.json` (the deprecated v2 API — cross-check against this before assuming something old-looking is just a docs typo; e.g. v2 had no top-level `/companies` POST at all, so behavior differences there are a genuine API redesign, not staleness). Every other core-API category used by the rest of this skill (`admin-catalog-*`, `admin-management-*`, `admin-payments-*`, `storefront-*`) has its own file in the same index — this is the same discovery mechanism, not B2B-specific. **How to use one:** download with `curl`/Bash and inspect with `jq`/python — these are 100s of KB to 1MB+, too large to dump into a WebFetch summarization pass or your own context wholesale. `jq '.paths | keys'` for the endpoint inventory, `jq '.paths["/x"]'` per-endpoint, and check `requestBody`/`responses` schemas and the plain-English `description` field (often states hard constraints in prose, like the orders-endpoint's 10-second window, that a bare schema table won't show). This is strictly more reliable than the `.md`-suffix/404-harvest scraping approach above (which is still useful only as a fallback for whatever these 79 files *don't* cover, or for prose-only guidance pages like getting-started/overview docs that aren't part of the OpenAPI spec).
